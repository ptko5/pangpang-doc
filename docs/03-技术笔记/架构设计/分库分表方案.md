## 2. 背景与目标

### 2.1 背景

- 单表数据量超过千万级后，MySQL 索引与查询性能显著下降
- 单库连接数、IO 与存储成为瓶颈
- 需要在不改变业务体验的前提下横向扩展

### 2.2 目标

| 目标 | 说明 |
|------|------|
| 突破单库容量与性能上限 | 通过分片水平扩展 |
| 保持业务透明 | 尽量减少对上层 SQL 的侵入 |
| 可平滑迁移 | 停机窗口可控，支持灰度 |
| 可回滚 | 迁移失败可回退原库 |

---

## 3. 拆分策略

### 3.1 垂直拆分（先做）

| 类型 | 说明 | 示例 |
|------|------|------|
| 垂直分库 | 按业务域拆分到不同库 | 订单库、用户库、商品库 |
| 垂直分表 | 大表按字段拆分（热/冷字段分离） | 订单主表 + 订单详情表 |

> **顺序**：优先垂直拆分（微服务边界天然支持），数据量仍超限再做水平拆分。

### 3.2 水平拆分（后做）

| 类型 | 说明 | 适用 |
|------|------|------|
| 水平分库 | 同一张表按分片键分布到多库 | 数据量大、连接数压力大 |
| 水平分表 | 同一张表分布到多表（同库） | 单表行数过大 |
| 库表结合 | 多库多表 | 通用 |

```text
order_db_0 ── order_0 ── order_1 ── order_2 ── order_3
order_db_1 ── order_0 ── order_1 ── order_2 ── order_3
```

## 4. 分片键选择

> 【强制】分片键必须选择查询频率最高、分布均匀的字段，一旦确定禁止更改。

| 分片键 | 优点 | 缺点 |
|--------|------|------|
| 主键取模 | 实现简单、分布均匀 | 范围查询需全分片扫描 |
| 用户 ID | 用户维度聚合天然均匀 | 其他维度查询受限 |
| 订单号（含分片位） | 按订单查询高效 | 生成规则依赖 |

### 4.1 取模路由示例

```sql
-- 分片数 = 8，分片号 = 订单号 % 8
-- 路由规则：order_${order_id % 8}
SELECT * FROM order_3 WHERE order_id = 100000003;
```

```java
// Java 路由示例
int shard = Math.floorMod(orderId, 8);
String table = "order_" + shard;
```

> 【推荐】分片数优先选择 2 的幂（如 8/16/32），便于二进制位运算与后续扩容。

## 5. 中间件选型对比

| 维度 | ShardingSphere | MyCat | 自研 |
|------|---------------|-------|------|
| 成熟度 | 高（Apache 顶级项目） | 中 | 低 |
| 支持语言 | Java 生态完善 | 多语言 | 定制 |
| 迁移成本 | 接入成本低 | 需配置 | 高 |
| 维护成本 | 社区活跃 | 更新较慢 | 高 |
| 推荐度 | **推荐** | 备选 | 不推荐 |

> **选型结论**：采用 Apache ShardingSphere，支持分片、读写分离、数据加密，符合 Spring Boot 4.x 技术栈。

## 6. 数据迁移方案

### 6.1 平滑迁移流程

1. **双写阶段**：新老库同时写入（通过 MQ/应用层双写），老库为主
2. **数据校验**：迁移工具回放 + 抽样比对（记录数、checksum）
3. **切换读**：读流量切到新库，观察数据一致性
4. **切换写**：应用切到新库，老库只读保留
5. **老库下线**：观察期后下线/归档

### 6.2 迁移工具

```bash
# 使用 DataX/官方工具做全量 + binlog 增量同步
datax.py -p /job/migrate_order.json
```

> 【强制】迁移必须经过「全量 + 增量 + 校验 + 演练」，并制定回滚预案。

## 7. 典型问题与对策

| 问题 | 说明 | 对策 |
|------|------|------|
| 分布式事务 | 跨库事务难以保证 | 本地消息表 / Seata AT / 最终一致 |
| 全局主键 | 自增主键冲突 | 雪花算法（Snowflake） |
| 跨分片查询 | 聚合/排序需合并 | 限制查询维度，或引入 ES 聚合层 |
| 扩容难题 | 分片数变更需重分布 | 预分片（2 的幂）+ 一致性哈希 |
| 数据倾斜 | 分片键分布不均 | 加盐/二次哈希 |

### 7.1 全局主键（雪花算法）

```java
@Bean
public IdGenerator idGenerator() {
    return new SnowflakeIdGenerator(workerId, datacenterId);
}
// 或使用 ShardingSphere 内置雪花算法
```

## 8. 风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 拆分布尔引入全局查询问题 | 高 | 明确查询路由约束，跨分片走 ES/汇总表 |
| 迁移数据不一致 | 高 | 双写 + 校验 + 灰度切换 |
| 分片键选错导致倾斜 | 高 | 上线前做数据分布评估 |
| 扩容成本高 | 中 | 预分片 + 自动化迁移工具 |
| 分布式事务复杂度 | 中 | 优先最终一致 + 幂等 |
