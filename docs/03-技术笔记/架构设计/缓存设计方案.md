## 2. 背景与目标

### 2.1 背景

- 核心接口存在大量重复查询，DB 压力大
- 需要降低响应时间、提升吞吐
- 需要统一缓存使用规范，避免滥用导致一致性问题

### 2.2 目标

| 目标 | 指标 |
|------|------|
| 热点接口 P95 降低 | < 100ms |
| DB QPS 下降 | 30%+ |
| 缓存命中率 | > 90% |
| 数据一致性与雪崩风险可控 | 有完整治理方案 |

## 3. 缓存模式对比

| 模式 | 读流程 | 写流程 | 适用 |
|------|--------|--------|------|
| **Cache Aside（旁路）** | 读缓存 → 未命中读 DB 并回填 | 写 DB 后删缓存 | 通用，推荐 |
| **Read/Write Through** | 缓存代理层统一处理 | 缓存写透到 DB | 需要抽象层 |
| **Write Behind（异步）** | 同旁路 | 先写缓存，异步落库 | 高写吞吐、可容忍丢失 |

> **选型结论**：默认使用 **Cache Aside**，写操作先更新 DB 再删除缓存；极高写入场景评估 Write Behind。

```text
读：App → Redis(命中返回) ─ 未命中 → DB → 回填 Redis
写：App → DB(先写) → 删除 Redis 缓存
```

## 4. 穿透 / 击穿 / 雪崩治理

### 4.1 缓存穿透（查不存在的数据）

| 手段 | 说明 |
|------|------|
| 缓存空值 | 查询为空也缓存（短 TTL，如 60s） |
| 布隆过滤器 | 前置判断 key 是否存在 |
| 参数校验 | 非法/超范围 key 直接拒绝 |

```java
// 缓存空值示例
if (value == null) {
    redis.set(key, "", 60); // 空值短 TTL，防止穿透
    return null;
}
```

### 4.2 缓存击穿（热点 key 过期）

| 手段 | 说明 |
|------|------|
| 互斥锁重建 | 单线程回源 DB，其余等待 |
| 逻辑过期 | value 中带过期时间，异步刷新 |
| 永不失效 + 定时更新 | 热点 key 主动刷新 |

```java
// 互斥锁重建示例
String lockKey = "lock:" + key;
if (tryLock(lockKey, 3)) {
    try {
        Object db = queryDB(key);
        redis.set(key, db, ttl);
    } finally {
        unlock(lockKey);
    }
}
```

### 4.3 缓存雪崩（大量 key 同时过期）

| 手段 | 说明 |
|------|------|
| TTL 随机化 | 过期时间加随机抖动 |
| 多级缓存 | 本地缓存 + Redis 兜底 |
| 熔断降级 | 缓存不可用时降级到 DB/降级响应 |

```java
// TTL 随机化示例
int ttl = baseTtl + ThreadLocalRandom.current().nextInt(300);
redis.set(key, value, ttl);
```

## 5. 一致性方案

### 5.1 先更新 DB 后删缓存（推荐）

```text
1. 更新 DB
2. 删除缓存（延迟双删可进一步保证）
```

- 优点：实现简单，命中率高
- 注意：删除失败时通过重试/MQ 兜底

### 5.2 延迟双删

```java
public void update(key, value) {
    redis.del(key);            // 第一次删
    db.update(key, value);     // 更新 DB
    Thread.sleep(500);         // 等待旧读回填过期
    redis.del(key);            // 第二次删（兜底）
}
```

> 【强制】缓存一致性必须结合业务容忍度选择；核心数据（余额/库存）优先保证强一致（删缓存 + 最终一致），非核心可弱一致。

## 6. Redis 集群选型

| 方案 | 容量 | 高可用 | 适用 |
|------|------|--------|------|
| 单机 + 哨兵 | 单机内存 | 主从自动切换 | 数据量小 |
| Cluster | 可水平扩展（16384 槽） | 分片高可用 | 大数据量 |
| Codis/自研代理 | 大集群 | 高 | 超大场景 |

> **选型结论**：生产使用 **Redis Cluster**（3 主 3 从起步），支持自动分片与故障转移；数据量小时可用哨兵。

## 7. 缓存使用规范

> 【强制】以下规范必须遵守：

| 规范 | 说明 |
|------|------|
| key 命名 | `业务:模块:ID`（如 `order:info:10001`） |
| 统一 TTL | 必须设置过期时间，禁止无限期 |
| 禁止大 key | 单 key 超过 1MB 拆分存储 |
| 禁止 `KEYS *` | 使用 `SCAN` |
| 缓存工具封装 | 统一封装 RedisUtil，禁止裸调 |

## 8. 风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 数据不一致 | 高 | 延迟双删 + MQ 兜底 + 业务补偿 |
| 雪崩/击穿 | 高 | TTL 随机 + 互斥锁 + 多级缓存 |
| 大 key 阻塞 | 中 | key 拆分 + 大小限制 |
| 缓存不可用 | 中 | 熔断降级 + 本地缓存 |
