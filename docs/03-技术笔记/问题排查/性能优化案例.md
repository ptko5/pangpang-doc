## 2. 优化流程（五步法）

1. **定位**：明确瓶颈（通过监控/压测/链路追踪）
2. **量化**：建立基线指标（QPS、响应时间、CPU/内存）
3. **优化**：针对性优化（代码/SQL/缓存/架构）
4. **验证**：复测对比前后指标
5. **沉淀**：输出优化记录，形成规范

> 【强制】优化必须量化验证，禁止「凭感觉」改动；每次优化只改一处，便于归因。

## 4. 后端优化案例（接口慢查询）

### 4.1 问题定位

- 订单列表接口 P95 = 1.2s，压测发现慢在 SQL 全表扫描

### 4.2 基线指标

| 指标 | 优化前 |
|------|--------|
| P95 | 1.2s |
| DB 扫描行数 | 200 万行 |
| QPS | 300 |

### 4.3 优化方案

```sql
-- 优化前：无索引条件过滤
SELECT * FROM `order` WHERE user_id = 10001 AND status = 1 ORDER BY created_at DESC;

-- 优化：联合索引覆盖查询条件
ALTER TABLE `order` ADD INDEX idx_user_status_created (user_id, status, created_at);

-- 优化：避免 SELECT *，只取必要字段
SELECT id, order_no, amount, status FROM `order` WHERE user_id = 10001 AND status = 1 ORDER BY created_at DESC LIMIT 20;
```

### 4.4 验证结果

| 指标 | 优化后 |
|------|--------|
| P95 | 180ms |
| 扫描行数 | 数百行 |
| QPS | 1500 |

### 4.5 沉淀规范

- 组合条件查询必须建联合索引（最左前缀原则）
- 禁止 `SELECT *`，按需取列
- 大列表查询必须分页

## 5. 缓存优化案例（热点数据）

### 5.1 问题定位

- 商品详情接口每次查库，DB QPS 高，响应慢

### 5.2 优化方案

```java
// 引入 Redis 缓存，读缓存 → 未命中回源 DB → 回填
public Product getProduct(Long id) {
    String key = "product:info:" + id;
    Object cache = redis.get(key);
    if (cache != null) {
        return (Product) cache;
    }
    Product p = productDao.findById(id);
    redis.set(key, p, 300 + randomJitter());
    return p;
}
```

### 5.3 验证结果

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| DB QPS | 5000 | 200 |
| 响应时间 | 80ms | 5ms |
| 命中率 | 0% | 96% |

### 5.4 沉淀规范

- 热点数据统一走缓存，TTL 随机防雪崩，详见 [缓存设计方案](../../03-技术笔记/架构设计/缓存设计方案.md)

## 6. 前端优化案例（首屏加载）

### 6.1 问题定位

- 首屏 LCP 3.5s，打包体积过大

### 6.2 优化方案

```text
1. 路由级代码分割（Vite 动态 import）
2. 静态资源 CDN + gzip/brotli
3. 图片懒加载与压缩
4. 组件按需引入（避免全量引入 UI 库）
```

```ts
// 路由级代码分割示例
const OrderList = () => import('@/views/order/OrderList.vue');
```

### 6.3 验证结果

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| LCP | 3.5s | 1.2s |
| 首屏 JS 体积 | 1.8MB | 650KB |

### 6.4 沉淀规范

- 首屏必须做代码分割与资源压缩，纳入前端工程化检查
