## 2. 核心理念：把 Skill 当纪律，不当框架

### 2.1 设计原点

本文档项目借鉴 mattpocock/skills（17万star）的核心立场：
> Skill 不应该是你需要刻意去调用的「框架」，而应该是你在做每一件事时都会自动遵守的「纪律」。

### 2.2 两层架构

```
┌──────────────────────────────────────────────────────────┐
│  User-invoked Skills（编排层 / Orchestration）            │
│  = 用户亲手打 /xxx 触发，职责是「编排工作流」              │
│  · 只能由用户触发，模型不能自动调用                        │
│  · 可以调用 Model-invoked Skills，但不能调用其他 User-invoked │
├──────────────────────────────────────────────────────────┤
│  Model-invoked Skills（纪律层 / Discipline）              │
│  = 模型可以自动调用，承载「可复用的检查约束」               │
│  · 写文档时自动触发，无需用户指令                          │
│  · 是 Skill 体系的主体，占 80% 的价值                     │
└──────────────────────────────────────────────────────────┘
```

### 2.3 铁律

> **A user-invoked skill may invoke model-invoked skills, but never another user-invoked one.**

翻译：用户编排技能可以调用纪律检查技能，但 **绝不可以** 调用另一个用户编排技能。

原因：防止循环依赖、确保职责单一、用户的意图是编排而非嵌套指令。

## 3. 目录结构规范

所有 Skill 定义存放于项目根目录的 `.skills/` 文件夹：

```
.skills/
├── README.md                                    # 本文件（技能体系总览）
├── user-invoked/                                # 用户编排层：用户打 /xxx 触发
│   ├── create-doc-from-link.md                  # 根据链接创建文档
│   ├── create-research-doc.md                   # 创建技术调研文档
│   ├── create-arch-design-doc.md                # 创建架构设计文档
│   ├── submit-docs-to-git.md                    # 提交文档到远程仓库
│   ├── audit-all-docs.md                        # 全库文档健康度审计
│   └── generate-toc.md                          # 生成全库目录索引
│
└── model-invoked/                               # 纪律层：模型自动触发
    ├── check-doc-structure.md                   # 检查文档结构（头部信息、结尾标记）
    ├── check-markdown-format.md                 # 检查 Markdown 格式（标题层级、代码块语言）
    ├── check-chinese-typography.md              # 检查中文排版（中英文空格、标点）
    ├── check-doc-placement.md                   # 检查文档归属目录是否正确
    ├── check-content-quality.md                 # 检查内容质量（无占位符、无空章节）
    ├── check-cross-references.md                # 检查交叉引用是否使用相对路径
    ├── check-image-resources.md                 # 检查图片资源是否在 assets 目录
    ├── check-git-commit-format.md               # 检查 Git 提交信息格式
    ├── check-branch-naming.md                   # 检查分支命名规范
    └── generate-checklist.md                    # 生成本次修改的落地检查清单
```

## 4. User-invoked Skills（编排层）

### 4.1 设计原则

- **用户意图单一**：每个 Skill 只解决一个明确的用户需求
- **内部编排 Model-invoked**：完成用户任务时，必须依次调用相关纪律检查 Skill
- **不可互相调用**：严格遵守铁律

### 4.2 技能清单

| 技能名称 | 触发命令 | 职责 | 调用的 Model-invoked Skills |
|---------|---------|------|---------------------------|
| **根据链接创建文档** | `/create-doc-from-link <url>` | 从外部链接提取内容，按文档类型归入正确目录，生成结构化文档 | check-doc-structure, check-markdown-format, check-chinese-typography, check-doc-placement, check-content-quality |
| **创建技术调研文档** | `/create-research-doc <主题>` | 创建符合技术调研模板的完整文档，包含背景、对比、建议、风险 | check-doc-structure, check-markdown-format, check-chinese-typography, check-doc-placement, check-content-quality, generate-checklist |
| **创建架构设计文档** | `/create-arch-design-doc <主题>` | 创建符合架构设计模板的完整文档，包含背景、方案对比、详细设计 | check-doc-structure, check-markdown-format, check-chinese-typography, check-doc-placement, check-content-quality, generate-checklist |
| **提交文档到远程** | `/submit-docs` | 执行完整的 Git 提交流程：检查变更 → 规范提交信息 → 创建分支 → 推送 | check-git-commit-format, check-branch-naming, generate-checklist |
| **全库文档审计** | `/audit-all-docs` | 遍历所有文档，执行所有纪律检查，输出健康度报告 | 所有 Model-invoked Skills（批量执行） |
| **生成目录索引** | `/generate-toc` | 扫描全库文档，生成 docs/README.md 的目录导航与交叉链接 | check-cross-references |

### 4.3 User-invoked Skill 定义格式

每个 `.md` 文件必须包含以下结构：

```markdown
---
name: create-doc-from-link
trigger: /create-doc-from-link <url>
layer: user-invoked
description: 根据外部链接创建结构化文档，自动归类到正确目录
invokes: [check-doc-structure, check-markdown-format, check-chinese-typography, check-doc-placement, check-content-quality]
---

## 执行步骤

1. 获取链接内容（优先 WebFetch，失败则回退浏览器自动化）
2. 分析内容类型，确定归属目录：
   - 技术选型/框架分析 → 03-技术笔记/新技术调研/
   - 架构方案/系统设计 → 03-技术笔记/架构设计/
   - 故障排查/性能调优 → 03-技术笔记/问题排查/
   - 源码分析/设计模式 → 03-技术笔记/源码阅读/
3. 创建文档，使用对应模板填充结构
4. 依次调用 invokes 中列出的纪律检查 Skill
5. 如有违规，自动修复或提示用户
6. 输出：创建完成的文档路径 + 检查结果汇总

## 失败处理

- 链接无法访问：提示用户提供备用链接或文本内容
- 内容无法分类：询问用户归属目录
- 纪律检查不通过且无法自动修复：输出违规明细供用户修改
```

## 5. Model-invoked Skills（纪律层）

### 5.1 设计原则

- **原子性**：每个 Skill 只检查一个维度的约束
- **幂等性**：重复执行不产生副作用
- **可组合**：多个 Skill 可以串行执行，互不依赖
- **自动修复优先**：能自动修复的问题不抛给用户

### 5.2 技能清单（纪律 = 自动执行的约束）

| 技能名称 | 检查维度 | 对应规范章节 | 自动修复 | 级别 |
|---------|---------|------------|---------|------|
| **check-doc-structure** | 文档头部信息、结尾标记、标题层级 | §3 元数据规范 + §5.1 标题层级 | ✅ 补全缺失部分 | 强制 |
| **check-markdown-format** | 标题递增、代码块语言、表格格式 | §5 Markdown 格式纪律 | ✅ 补全代码块语言 | 强制 |
| **check-chinese-typography** | 中英文空格、全角标点、反引号术语 | §5.2 中文排版 | ✅ 自动插入空格 | 强制 |
| **check-doc-placement** | 文档目录归属、子目录分类正确 | §4 目录结构规则 | ❌ 需人工判断 | 强制 |
| **check-content-quality** | 占位符文本、空章节、TODO/FIXME | §6.1 禁止内容 | ❌ 必须人工修改 | 禁止 |
| **check-cross-references** | 内部引用相对路径、链接有效性 | §6.2 交叉引用 | ✅ 修正路径格式 | 推荐 |
| **check-image-resources** | 图片路径、是否引用外部URL | §6.3 图片与资源 | ❌ 需移动文件 | 强制 |
| **check-git-commit-format** | 提交信息格式、类型、模块 | Git工作流 §3 提交注释 | ✅ 格式化提交信息 | 强制 |
| **check-branch-naming** | 分支命名前缀、描述规范 | Git工作流 §2.2 分支创建 | ❌ 需重建分支 | 强制 |
| **generate-checklist** | 根据本次变更生成检查清单 | 所有规范的落地检查 | ✅ 自动生成 | 辅助 |

### 5.3 Model-invoked Skill 定义格式

每个 `.md` 文件必须包含以下结构：

```markdown
---
name: check-doc-structure
layer: model-invoked
description: 检查文档结构是否符合规范（头部信息块、标题层级、结尾标记）
corresponds: [文档书写规范 §3, §5.1, §5.5]
can-autofix: true
severity: mandatory
---

## 检查规则

### R1: 文档头部信息块（强制）
- 前8行必须包含 `# 标题` + `## 1. 文档说明` + 4行属性表格
- 属性表必须包含：文档版本、生效日期、适用范围、作者
- 生效日期格式：YYYY-MM-DD
- 版本号格式：V<主>.<次>

### R2: 标题层级（强制）
- 有且仅有一个 `#` 一级标题
- 标题层级严格递增，禁止跳级（H1→H3 不允许）

### R3: 文档结尾标记（强制）
- 文档末尾必须包含：`---` + `**文档结束**` + 版权声明行

## 自动修复逻辑

- R1: 缺失头部信息时，根据文档内容推断并插入模板
- R2: 检测到跳级时，自动将 H3 降为 H2（逐级补齐）
- R3: 缺失结尾标记时，自动追加

## 输出格式

```json
{
  "passed": false,
  "violations": [
    {"rule": "R1", "line": 1, "message": "缺失文档说明表格", "autofixed": false},
    {"rule": "R3", "line": null, "message": "缺失结尾标记", "autofixed": true}
  ],
  "summary": "共发现2项违规，1项已自动修复"
}
```
```

## 6. 技能定义文件规范

### 6.1 Front Matter 字段说明

```yaml
---
name: skill-name                    # 技能唯一标识，kebab-case
trigger: /command <arg>             # User-invoked 专属：触发命令
layer: user-invoked | model-invoked  # 所属层级
description: 一句话描述技能职责       # 简短说明
invokes: [other-skill-a, ...]       # User-invoked 专属：调用的纪律技能
corresponds: [规范章节引用]          # Model-invoked 专属：对应规范条目
can-autofix: true | false           # Model-invoked 专属：是否可自动修复
severity: mandatory | advisory      # Model-invoked 专属：严重级别
---
```

### 6.2 文件命名

- 全部使用 **kebab-case**：`check-doc-structure.md`
- 前缀约定：
  - User-invoked: 动词开头 `create-`、`submit-`、`audit-`、`generate-`
  - Model-invoked: `check-`（检查）或 `generate-`（生成辅助）

## 7. 执行流程示例

### 7.1 场景：用户执行 `/create-doc-from-link https://example.com/article`

```
用户输入 /create-doc-from-link
        │
        ▼
┌─────────────────────────────────┐
│ User-invoked: create-doc-from-link │
│  1. 抓取链接内容                  │
│  2. 分析类型 → 归入新技术调研/     │
│  3. 创建文档草稿                  │
│  4. 串行调用以下纪律检查：         │
│     ├─► check-doc-structure    ✅ │
│     ├─► check-markdown-format  ✅ │
│     ├─► check-chinese-typography✅│
│     ├─► check-doc-placement    ✅ │
│     └─► check-content-quality  ❌ │
│        → 发现「（待补充）」占位符  │
│        → 无法自动修复，提示用户    │
│  5. 输出：文档路径 + 检查报告      │
└─────────────────────────────────┘
```

### 7.2 场景：用户执行 `/submit-docs`

```
用户输入 /submit-docs
        │
        ▼
┌─────────────────────────────────┐
│ User-invoked: submit-docs        │
│  1. git status → 获取变更文件列表 │
│  2. 对每个变更的 .md 文件执行：    │
│     所有 Model-invoked 检查      │
│  3. 全通过 → 下一步              │
│     不通过 → 输出违规列表，终止    │
│  4. check-branch-naming ✅       │
│  5. 生成规范的提交信息：          │
│     docs(模块): 简短描述           │
│  6. check-git-commit-format ✅   │
│  7. git add / commit / push      │
│  8. generate-checklist → 输出清单 │
└─────────────────────────────────┘
```

## 9. 技能扩展指南

### 9.1 新增 User-invoked Skill

1. 明确用户的 **单一意图**（不要做两件事）
2. 列出执行过程中需要遵守的 **纪律**，对应到已有或新增的 Model-invoked Skill
3. 在 `.skills/user-invoked/` 下创建定义文件
4. 编写 Front Matter + 执行步骤 + 失败处理

### 9.2 新增 Model-invoked Skill

1. 确认对应 **规范章节**（没有规范先补规范，不要先写检查器）
2. 拆分为 **原子检查规则**（R1, R2...）
3. 判断是否 **可自动修复**
4. 在 `.skills/model-invoked/` 下创建定义文件
5. 编写检查规则 + 自动修复逻辑 + 输出格式
