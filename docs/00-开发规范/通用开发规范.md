## 2. 代码版本控制（Git）

### 2.1 分支命名策略

| 前缀 | 用途说明 |
|-|-|
| `feature/` | 新增功能开发 |
| `bugfix/` | 常规缺陷修复 |
| `hotfix/` | 线上紧急修复 |
| `release/` | 版本发布准备 |
| `refactor/` | 代码重构（无功能变化） |
| `docs/` | 文档更新 |

命名格式：`前缀 + 简短的描述性名称`，单词间用连字符分隔。例如：`feature/user-authentication`。

### 2.2 仓库结构

| 分支 | 性质 | 说明 |
|-|-|-|
| `main` / `master` | 保护分支 | 始终代表可发布状态，只接受合并不允许直接推送 |
| `develop` | 开发分支 | 集成分支，功能完成后合并至此 |
| `feature/*` | 功能分支 | 从 develop 拉取，开发完成后合并回 develop |
| `bugfix/*` | 修复分支 | 从 develop 拉取，修复完成后合并回 develop |
| `hotfix/*` | 热修分支 | 从 main 拉取，修复完成后同时合并到 main 和 develop |

### 2.3 分支管理流程

- 所有新功能与缺陷修复必须从对应基准分支创建独立分支，禁止在保护分支上直接开发
- 功能分支应尽快合并，避免长期独立存在导致合并冲突积压
- 合并前必须通过 CI/CD 流水线检查
- hotfix 分支需指定专人负责，合并后应立即触发发布流程
- 分支合并应使用 `--no-ff` 策略，保留合并历史便于追溯

## 3. 代码提交规范（Commit Message）

### 3.1 提交信息格式

采用 Angular 规范：`<type>(<scope>): <description>`

| 类型 | 适用场景 |
|-|-|
| `feat` | 新增功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档更新 |
| `style` | 格式调整（不影响代码逻辑） |
| `refactor` | 重构（不修复也不新增功能） |
| `test` | 测试相关 |
| `chore` | 构建、工具、依赖更新等杂项 |
| `perf` | 性能优化 |
| `ci` | CI/CD 配置变更 |

### 3.2 提交粒度原则

- **原子性**：每个提交只做一件事
- **完整性**：提交应是一个独立可用的状态
- **可回滚**：每个提交都应可单独回滚
- **频率**：鼓励频繁提交，但必须保证质量

## 4. 代码审查流程（Code Review）

### 4.1 PR 创建规范

- **标题**：清晰描述变更内容，遵循提交信息格式
- **描述**：说明变更动机、变更内容、影响范围、测试情况
- **关联任务**：通过 `Closes #<issue-number>` 关联相关任务
- **审查者**：指定至少一名熟悉该模块的团队成员
- **自审清单**：提交者应先自行检查代码是否符合规范

### 4.2 Review 注意事项

| 检查维度 | 具体要点 |
|-|-|
| **功能正确性** | 逻辑是否符合需求，边界条件是否处理 |
| **代码质量** | 是否符合命名、注释、错误处理等要求 |
| **安全性** | 是否存在注入、越权、信息泄露等安全风险 |
| **性能影响** | 是否有明显的性能隐患，如 N+1 查询 |
| **测试覆盖** | 新增逻辑是否有对应测试 |
| **向后兼容** | 变更是否影响现有接口或数据格式 |

### 4.3 合并条件

- 必须获得至少一人审批通过方可合并
- 所有 CI 检查必须通过
- 禁止绕过审查直接合并到保护分支
- hotfix 分支在紧急情况下可先合并后补审查

## 5. 项目目录结构

### 5.1 通用分层原则

| 目录 | 用途 |
|-|-|
| `src/` | 源代码 |
| `config/` | 配置文件 |
| `test/` | 测试代码 |
| `docs/` | 项目文档 |
| `scripts/` | 构建、部署、辅助脚本 |
| `assets/` | 静态资源 |
| `build/` | 构建产物（不纳入版本控制） |

### 5.2 模块划分规范

- 按业务领域或功能模块划分目录
- 每个模块应职责单一，模块间通过定义良好的接口交互
- 核心公共逻辑抽取到独立模块，供各业务模块复用

## 6. 命名约定

### 6.1 通用命名原则

- **清晰优先**：命名应自解释，避免过度缩写
- **一致性**：同类事物采用统一的命名风格
- **避免缩写歧义**：除非是领域内公认的通用缩写（API、URL、ID）
- **反映职责**：命名应体现其业务含义

### 6.2 常见命名场景

- **变量**：名词或名词短语，采用有意义的名称
- **函数/方法**：动词或动词短语，如 `getUserById`
- **类/类型**：名词短语，采用 PascalCase
- **常量**：全大写 + 下划线（`MAX_RETRY_COUNT`）
- **布尔值**：使用 `is`、`has`、`can` 等前缀

## 7. 注释规范

### 7.1 注释目的

注释应说明**为何这样做**，而非**做了什么**。

### 7.2 标准化注释标记

| 标记 | 含义与用法 |
|-|-|
| `TODO:` | 待完成事项 |
| `FIXME:` | 已知问题，需要修复 |
| `HACK:` | 临时方案，需要后续改进 |
| `NOTE:` | 重要提示 |
| `DEPRECATED:` | 废弃标记 |

### 7.3 禁止注释的内容

- 显而易见的代码逻辑
- 过时、无效、误导性的注释
- 被注释掉的代码块（删除而非注释）
- 用于调试的临时注释

## 8. 错误处理

### 8.1 错误分类

| 类型 | 特征 | 处理原则 |
|-|-|-|
| **业务异常** | 业务规则触发的预期错误 | 返回明确的业务错误码和提示信息 |
| **系统异常** | 基础设施或代码缺陷引起的非预期错误 | 记录详细日志，返回通用错误信息 |

### 8.2 错误返回规范

- 接口统一错误响应格式，包含错误码、错误信息、请求 ID
- 面向用户的错误信息应简洁友好，避免暴露技术栈
- 禁止吞掉异常而不做任何处理
- 异常应在其能正确处理的最近层级捕获

---

## 9. 安全性要求

### 9.1 通用安全原则

- **输入校验**：所有外部输入必须进行校验和清理
- **输出编码**：输出到前端的内容必须进行适当编码，防止 XSS
- **敏感信息不硬编码**：密钥、令牌等严禁硬编码在代码中
- **最小权限原则**：服务和进程只申请其所需的最小权限

### 9.2 日志脱敏要求

| 字段类型 | 脱敏方式 |
|-|-|
| 手机号 | 保留前三位和后四位，中间用星号替代 |
| 身份证号 | 只显示前四位和后四位 |
| 银行卡号 | 只显示后四位 |
| 密码/密钥 | 完全隐藏 |
| 邮箱 | 保留域名和首字符，其余用星号替代 |

## 10. 性能优化原则

### 10.1 通用性能意识

- **避免重复计算**：将重复调用的结果缓存
- **合理缓存**：对读多写少的数据使用缓存
- **及时释放资源**：数据库连接、网络连接等使用后应及时释放
- **延迟加载**：非核心路径的数据采用懒加载策略
- **批量操作**：批量处理替代循环单条操作

### 10.2 数据库与查询优化

- 避免全表扫描，通过索引优化查询性能
- 禁止在循环中执行数据库查询
- 分页查询应有合理的页大小限制
- 定期分析慢查询日志，针对性优化高频慢查询
