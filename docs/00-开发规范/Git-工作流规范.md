## 2. Git分支模型

### 2.1 分支类型定义

| 分支类型 | 命名规则 | 生命周期 | 用途说明 |
|---------|---------|---------|---------|
| **主分支** | `main` | 永久 | 生产环境代码基线，仅接受合并请求，禁止直接提交 |
| **开发分支** | `develop` | 永久 | 日常开发集成分支，所有功能分支合并至此 |
| **功能分支** | `feature/xxx` | 临时 | 新功能开发，从develop创建，完成后合并回develop |
| **修复分支** | `fix/xxx` | 临时 | Bug修复，从develop创建，完成后合并回develop |
| **发布分支** | `release/x.y.z` | 临时 | 预发布准备，从develop创建，测试通过后合并至main和develop |
| **紧急修复分支** | `hotfix/xxx` | 临时 | 生产紧急修复，从main创建，修复后合并至main和develop |

### 2.2 分支流转流程

```
                    ┌─────────────────┐
                    │     main        │ ← 生产环境基线
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
        ┌─────────┐    ┌─────────┐    ┌──────────┐
        │ release │←──│ develop │──→│ hotfix   │
        │/x.y.z   │    │         │    │/xxx      │
        └────┬────┘    └────┬────┘    └────┬─────┘
             │              │              │
             │              ▼              │
             │    ┌──────────────┐         │
             │    │  feature/xxx │         │
             │    │  fix/xxx     │         │
             │    └──────┬───────┘         │
             │           │                 │
             └───────────┴─────────────────┘
                         │
                         ▼
                    ┌─────────┐
                    │  MR合并  │
                    └─────────┘
```

### 2.3 分支操作规范

#### 【强制】主分支保护

- `main` 和 `develop` 分支必须开启 **分支保护**，禁止直接推送（push）
- 所有代码变更必须通过 **合并请求（MR）** 进行
- MR必须经过至少 **1位代码评审人** 批准后才能合并
- 合并前必须通过 **CI流水线** 构建和测试验证

#### 【强制】分支创建规则

- **功能分支**：从 `develop` 分支创建，命名为 `feature/功能名`
  ```bash
  git checkout -b feature/user-auth develop
  ```
- **修复分支**：从 `develop` 分支创建，命名为 `fix/问题描述`
  ```bash
  git checkout -b fix/login-error develop
  ```
- **发布分支**：从 `develop` 分支创建，命名为 `release/版本号`
  ```bash
  git checkout -b release/1.0.0 develop
  ```
- **紧急修复分支**：从 `main` 分支创建，命名为 `hotfix/问题描述`
  ```bash
  git checkout -b hotfix/production-crash main
  ```

#### 【推荐】分支清理

- 功能/修复分支合并后，**及时删除** 本地和远程分支
- 发布分支合并后，建议保留一段时间供回溯，随后删除
- 定期执行分支清理：
  ```bash
  git fetch --prune
  git branch -d feature/user-auth
  git push origin --delete feature/user-auth
  ```

## 3. 提交注释规范

### 3.1 提交信息格式

【强制】所有提交信息必须遵循以下格式：

```
<类型>(<模块>): <简短描述>

<详细描述（可选）>

<关联信息（可选）>
```

### 3.2 提交类型定义

| 类型 | 说明 | 使用场景 |
|------|------|---------|
| `feat` | 新功能 | 新增业务功能、新增API接口、新增页面 |
| `fix` | Bug修复 | 修复线上问题、修复测试用例失败 |
| `refactor` | 重构 | 代码重构、优化，不改变功能逻辑 |
| `docs` | 文档 | 更新技术文档、注释、README |
| `style` | 样式 | 代码格式调整、不影响逻辑的改动 |
| `test` | 测试 | 新增/修改测试用例 |
| `chore` | 杂项 | 构建脚本、配置文件、依赖更新 |
| `perf` | 性能 | 性能优化、资源优化 |
| `revert` | 回滚 | 撤销之前的提交 |

### 3.3 提交信息示例

#### ✅ 正确示例

```bash
# 新功能
git commit -m "feat(user): 新增用户注册功能

- 添加用户注册API接口
- 实现密码加密存储
- 新增注册表单验证逻辑

关联需求: REQ-001"

# Bug修复
git commit -m "fix(order): 修复订单状态更新失败问题

修复订单支付成功后状态未正确更新的Bug
根因: 事务提交顺序错误

关联Bug: BUG-001"

# 重构
git commit -m "refactor(auth): 重构JWT鉴权模块

- 提取Token生成逻辑为独立服务
- 使用JDK25虚拟线程优化Token刷新性能
- 代码行数减少30%"

# 文档更新
git commit -m "docs(规范): 更新数据库设计规范"

# 依赖更新
git commit -m "chore(deps): 更新Spring Boot至4.0.0"
```

#### ❌ 错误示例

```bash
# 错误：描述过于模糊
git commit -m "修改了一些代码"

# 错误：缺少类型和模块
git commit -m "用户注册功能"

# 错误：提交信息过长，应拆分为多个提交
git commit -m "新增用户管理、订单管理、支付模块，包含所有功能..."

# 错误：一次性提交多个不相关的修改
git commit -m "修复登录Bug和更新文档"
```

### 3.4 提交粒度规范

#### 【强制】提交粒度

- **单次提交只包含一个逻辑单元**：一个功能、一个Bug修复、一个重构点
- 避免"大爆炸"提交：一个提交包含多个不相关功能的修改
- 逻辑相关的代码必须在同一个提交中

#### 【推荐】提交顺序

- 先提交 **工具类/基础组件** 的修改
- 再提交 **业务逻辑** 的修改
- 最后提交 **测试用例** 和 **文档** 的更新

## 4. MR/CR（代码评审）流程

### 4.1 MR创建规范

#### 【强制】MR标题格式

```
<类型>(<模块>): <简短描述> - <分支名>
```

示例：
```
feat(user): 新增用户注册功能 - feature/user-auth
fix(order): 修复订单状态更新失败 - fix/order-status
```

#### 【强制】MR描述内容

MR描述必须包含以下内容：

| 内容项 | 说明 |
|-------|------|
| **需求/问题描述** | 该MR解决什么问题或实现什么功能 |
| **变更内容** | 具体修改了哪些文件、哪些逻辑 |
| **测试情况** | 是否通过所有测试、新增了哪些测试用例 |
| **影响范围** | 可能影响哪些模块、哪些接口 |
| **关联链接** | 关联的需求编号、Bug编号、设计文档链接 |

#### 【推荐】MR大小控制

- 单个MR的代码变更行数建议控制在 **500行以内**
- 如果变更量较大，应拆分为多个MR，按模块或功能点分批提交
- 大型重构建议先提交设计方案进行评审

### 4.2 代码评审规范

#### 【强制】评审人选择

- MR创建者必须指定 **至少1位** 相关模块的负责人作为评审人
- 复杂业务逻辑变更必须指定 **架构师** 进行评审
- 涉及安全相关代码变更必须指定 **安全工程师** 进行评审

#### 【强制】评审标准

评审人必须检查以下内容：

| 检查项 | 说明 |
|-------|------|
| **代码规范** | 是否符合公司编码规范（命名、注释、格式） |
| **业务逻辑** | 是否正确实现需求、是否有逻辑漏洞 |
| **安全性** | 是否存在安全隐患（SQL注入、XSS、敏感信息泄露） |
| **性能** | 是否有性能问题（N+1查询、大循环、内存泄漏） |
| **测试覆盖** | 是否有足够的测试用例覆盖 |
| **可维护性** | 代码是否易于理解和维护 |
| **依赖变更** | 是否引入不必要的依赖、版本是否兼容 |

#### 【推荐】评审反馈规范

- 评审意见必须 **具体、明确**，指出问题所在和改进建议
- 避免模糊的评价如"代码写得不好"，应说明具体问题
- 对于可接受的小问题，可以使用"建议改进"标记，不阻塞合并

### 4.3 MR合并规范

#### 【强制】合并前置条件

MR必须满足以下条件才能合并：

1. ✅ 所有评审人 **批准**（Approve）
2. ✅ CI流水线 **构建通过**
3. ✅ 所有测试用例 **执行通过**
4. ✅ SonarQube代码质量扫描 **无阻塞级问题**
5. ✅ 无 **未解决的冲突**

#### 【强制】合并方式

| 分支类型 | 合并方式 | 说明 |
|---------|---------|------|
| 功能/修复分支 → develop | **Squash Merge** | 将多个提交压缩为一个，保持提交历史清晰 |
| release → main | **Create Merge Commit** | 保留完整提交历史，便于追溯 |
| release → develop | **Create Merge Commit** | 同步发布分支的修复到开发分支 |
| hotfix → main | **Create Merge Commit** | 保留紧急修复的完整记录 |
| hotfix → develop | **Create Merge Commit** | 同步紧急修复到开发分支 |

#### 【禁止】

- 禁止在存在 **未解决冲突** 的情况下强行合并
- 禁止跳过CI测试直接合并
- 禁止在评审人提出 **阻塞级问题** 未解决时合并

## 5. 版本号规则

### 5.1 版本号格式

【强制】版本号采用 **语义化版本（Semantic Versioning）**：

```
<主版本号>.<次版本号>.<修订版本号>[-预发布版本]
```

示例：
- `1.0.0` - 正式发布版本
- `1.1.0` - 新增功能，不兼容变更
- `1.0.1` - Bug修复，兼容变更
- `1.0.0-beta.1` - Beta预发布版本
- `1.0.0-SNAPSHOT` - 开发中快照版本

### 5.2 版本号变更规则

| 变更类型 | 版本号变更 | 说明 |
|---------|----------|------|
| **不兼容的API变更** | 主版本号 + 1 | 删除接口、修改接口参数、修改返回值结构 |
| **向后兼容的功能新增** | 次版本号 + 1 | 新增API接口、新增功能模块 |
| **向后兼容的Bug修复** | 修订版本号 + 1 | 修复已知问题、性能优化 |
| **预发布版本** | 添加预发布标识 | `-alpha`、`-beta`、`-rc` |

### 5.3 版本发布流程

```
develop → release/x.y.z → 测试验证 → main (打Tag) → 生产发布
         │                                         │
         └─────────────────────────────────────────┘
                       同步修复
```

#### 【强制】Tag命名规则

```
v<主版本号>.<次版本号>.<修订版本号>
```

示例：
```bash
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0
```

### 5.4 版本管理规范

#### 【推荐】版本归档

- 每个正式版本发布后，在代码仓库中 **创建Release记录**
- Release记录包含：变更日志、新增功能、修复问题、已知问题
- 重要版本应保留完整的构建产物归档

#### 【推荐】变更日志（CHANGELOG）

每次发布必须更新 CHANGELOG.md，包含：

| 章节 | 内容 |
|------|------|
| **新增（Added）** | 新增的功能、接口、页面 |
| **变更（Changed）** | 修改的逻辑、调整的参数 |
| **修复（Fixed）** | 修复的Bug、问题 |
| **删除（Removed）** | 删除的接口、功能、依赖 |

## 6. 团队协作规范

### 6.1 代码所有权

#### 【推荐】模块负责人制度

- 每个业务模块指定 **模块负责人**
- 模块负责人对模块的代码质量、架构设计负责
- 跨模块修改必须通知相关模块负责人

### 6.2 代码冻结期

#### 【推荐】发布前冻结

- 发布分支创建后，进入 **代码冻结期**
- 冻结期间只允许 **Bug修复**，禁止新增功能
- 冻结期持续至测试通过、版本发布

### 6.3 冲突处理

#### 【强制】冲突解决

- 分支合并产生冲突时，由 **分支创建者** 负责解决
- 冲突解决后必须进行 **本地测试**，确保功能正常
- 复杂冲突应与相关开发人员 **沟通确认** 后再解决

## 7. 落地检查清单

| 序号 | 检查项 | 检查方式 | 责任人 |
|------|--------|---------|--------|
| 1 | `main` 和 `develop` 分支是否开启保护 | 查看Git仓库设置 | 仓库管理员 |
| 2 | 分支命名是否符合 `feature/xxx`、`fix/xxx` 规则 | 检查分支列表 | 开发人员 |
| 3 | 提交信息是否包含类型、模块、描述 | 检查Git日志 | 开发人员 |
| 4 | 单次提交是否只包含一个逻辑单元 | 检查提交内容 | 代码评审人 |
| 5 | MR是否包含完整的描述信息 | 检查MR内容 | MR创建者 |
| 6 | MR是否经过至少1位评审人批准 | 检查MR状态 | MR创建者 |
| 7 | CI流水线是否通过 | 检查CI状态 | MR创建者 |
| 8 | 版本号是否符合语义化版本规范 | 检查Tag命名 | 发布负责人 |
| 9 | 是否及时清理已合并的临时分支 | 检查分支列表 | 开发人员 |
| 10 | CHANGELOG是否及时更新 | 检查CHANGELOG.md | 发布负责人 |
