## 2. 代码规范

### 2.1 命名规范

| 类型 | 命名规则 |
|-|-|
| 变量 | 小驼峰（camelCase）：userName, orderCount |
| 常量 | 全大写下划线分隔：MAX_RETRY_COUNT, API_TIMEOUT |
| 函数/方法 | 小驼峰或下划线：getUserById |
| 类名 | 大驼峰（PascalCase）：UserService, OrderController |
| 模块/包 | 全小写下划线或中划线：user_service, user-service |
| 数据库表 | 全小写下划线，复数名词：users, order_items |
| 数据库字段 | 全小写下划线：user_name, created_at |

### 2.2 代码格式

- 缩进统一使用 4 空格，禁止使用 Tab
- 单行字符数不超过 120，超出时换行并对齐
- 方法之间保留 1-2 空行，类之间保留 2 空行
- import 语句按字母顺序排列，标准库在前，第三方库在后

### 2.3 注释规范

- 公共 API 必须编写 Javadoc / DocString 说明参数和返回值
- 复杂业务逻辑需添加行内注释说明意图
- 禁止使用废弃代码的注释（直接删除）
- TODO/FIXME 注释必须附带负责人和日期

### 2.4 目录结构

```bash
project-root/
├── cmd/                # 入口文件
│   └── server/
│       └── main.go
├── internal/           # 私有业务代码
│   ├── handler/        # 接口层
│   ├── service/        # 业务逻辑层
│   ├── repository/     # 数据访问层
│   └── model/          # 数据模型
├── pkg/                # 公共可复用包
├── config/             # 配置文件
├── scripts/            # 部署脚本
└── docs/               # 文档
```

## 3. Git 协作规范

### 3.1 分支命名策略

| 分支类型 | 命名格式 |
|-|-|
| 特性分支 | feature/功能简述 |
| 修复分支 | fix/问题简述 |
| 发布分支 | release/v版本号 |
| 热修复分支 | hotfix/问题简述 |

### 3.2 Commit Message 规范

采用 Conventional Commits 标准格式：

```bash
<type>(<scope>): <subject>

[可选正文]

[可选脚注]
```

| 类型 | 说明 |
|-|-|
| feat | 新功能 |
| fix | 缺陷修复 |
| docs | 文档更新 |
| style | 格式调整 |
| refactor | 重构 |
| test | 测试相关 |
| chore | 构建/工具变更 |

## 4. API 设计规范

### 4.1 RESTful 风格指南

| 操作 | HTTP 方法 |
|-|-|
| 查询资源 | GET /users |
| 获取单个资源 | GET /users/{id} |
| 创建资源 | POST /users |
| 更新资源 | PUT /users/{id} 或 PATCH /users/{id} |
| 删除资源 | DELETE /users/{id} |

### 4.2 接口命名

- 使用名词复数形式表示资源：/users, /orders
- 避免在 URL 中使用动词
- 层级嵌套不超过 2 层：/users/{id}/orders
- 使用 kebab-case

### 4.3 错误码设计

```json
{
  "code": 10001,
  "message": "用户不存在",
  "data": null,
  "request_id": "req_abc123"
}
```

| 错误码范围 | 含义 |
|-|-|
| 1xxxx | 系统级错误 |
| 2xxxx | 认证授权错误 |
| 3xxxx | 参数校验错误 |
| 4xxxx | 业务逻辑错误 |
| 5xxxx | 第三方服务错误 |

### 4.4 版本管理

- 使用 URL 路径版本控制：/api/v1/users
- 主版本号不兼容时递增，旧版本保留至少 3 个月

## 5. 数据库规范

### 5.1 表/字段命名

- 表名使用小写字母和下划线，全小写复数名词
- 主键统一命名：id（BIGINT，自增）
- 时间字段命名：created_at, updated_at, deleted_at
- 外键命名：xxx_id

### 5.2 索引设计原则

- 高频查询条件字段建立索引
- 单表索引数量不超过 5 个
- 组合索引遵循最左前缀原则
- 避免在区分度低的字段上建索引

### 5.3 事务使用规范

- 事务范围尽量小，避免长事务
- 读已提交（Read Committed）为默认隔离级别
- 批量操作需评估锁竞争风险
- 分布式事务优先使用 Saga 或 TCC 模式

## 6. 安全规范

### 6.1 认证鉴权

- 使用 JWT 或 OAuth2.0 进行身份认证
- Token 设置合理有效期（Access Token ≤ 1 小时）
- 敏感接口必须二次验证
- 实现基于角色的访问控制（RBAC）

### 6.2 敏感数据处理

- 密码使用 bcrypt/Argon2 等强哈希算法存储
- 敏感数据在日志中脱敏
- 敏感数据传输必须使用 HTTPS
- 密钥使用配置中心管理，禁止硬编码

### 6.3 输入校验

- 所有外部输入必须校验
- SQL 参数化查询防止注入攻击
- XSS 攻击：输出时转义 HTML 特殊字符

## 7. 日志与监控

### 7.1 日志级别规范

| 级别 | 使用场景 |
|-|-|
| DEBUG | 开发调试信息，生产环境禁用 |
| INFO | 正常业务流程记录 |
| WARN | 潜在问题但不影响功能 |
| ERROR | 错误，需要关注但不影响整体 |
| FATAL | 严重错误，导致系统不可用 |

### 7.2 日志内容规范

- 包含：时间戳、请求 ID、用户 ID、操作类型、关键参数、耗时、结果
- 敏感字段自动脱敏
- 结构化日志格式（JSON）便于检索分析

```json
{
  "time": "2026-05-18T10:30:00Z",
  "level": "INFO",
  "request_id": "req_abc123",
  "user_id": 10001,
  "action": "create_order",
  "duration_ms": 150,
  "status": "success"
}
```

### 7.3 异常处理原则

- 统一异常捕获，区分业务异常和系统异常
- 异常信息包含错误码和友好提示
- 禁止将敏感信息暴露给客户端
- 异常需记录完整上下文便于排查

## 8. 部署与运维

### 8.1 环境管理

| 环境 | 用途 |
|-|-|
| dev | 开发联调，功能验证 |
| test | 集成测试、性能测试 |
| staging | 预发布验证，与生产一致 |
| prod | 生产环境 |

### 8.2 配置管理

- 环境变量作为配置注入的主要方式
- 使用配置中心（Apollo / Nacos）管理不同环境配置
- 敏感配置加密存储
- 配置变更需记录审计日志
