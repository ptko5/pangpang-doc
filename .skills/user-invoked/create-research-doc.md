## 执行步骤

### Step 1: 接收主题参数

- 必填：`<主题>` - 调研的技术或方案名称
- 可选附加信息：背景描述、关注点、对比方案

### Step 2: 收集资料（如需要）

如果主题涉及：
- 具体技术栈（如国际化方案、ORM选型）→ 先进行 WebSearch 搜索最新资料
- 已有内部文档 → 先检索 docs/ 目录下的相关内容

### Step 3: 创建文档

**目标目录**：`/workspace/docs/03-技术笔记/新技术调研/`

**文件名**：`<主题>-调研.md`（kebab-case 处理）

**文档骨架**：

```markdown
# <主题>调研

## 1. 文档说明

| 属性 | 说明 |
|------|------|
| 文档版本 | V1.0 |
| 生效日期 | YYYY-MM-DD |
| 适用范围 | 所有研发团队 |
| 作者 | 架构组 |

---

## 2. 背景与动机

### 2.1 业务背景
（为什么需要这项技术/方案？解决什么问题？）

### 2.2 现状分析
（当前方案的痛点、瓶颈、限制）

### 2.3 调研目标
（本次调研要回答哪些问题、输出什么结论）

---

## 3. 核心概念

### 3.1 基础术语
（关键术语定义、行业标准解读）

### 3.2 原理机制
（核心工作原理、架构图、流程图）

---

## 4. 方案对比分析

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 架构职责 | | | |
| 接入成本 | | | |
| 性能表现 | | | |
| 维护成本 | | | |
| 社区生态 | | | |
| 团队适配度 | | | |
| **综合评分** | | | |

### 4.1 方案 A 详细分析
- 优势
- 劣势
- 适用场景

### 4.2 方案 B 详细分析
- 优势
- 劣势
- 适用场景

---

## 5. 实施建议

### 5.1 推荐方案
（明确给出推荐选型 + 核心理由）

### 5.2 分阶段实施路径
| 阶段 | 时间 | 交付物 |
|------|------|--------|
| Phase 1 | Week 1-2 | POC 验证报告 |
| Phase 2 | Week 3-4 | 试点接入 |
| Phase 3 | Week 5-8 | 全量推广 |

### 5.3 团队技能准备
（需要学习的内容、培训计划）

---

## 6. 风险评估

| 风险项 | 概率 | 影响 | 缓解措施 |
|--------|------|------|---------|
| | 高/中/低 | 高/中/低 | |

---

## 7. 落地检查清单

| 序号 | 检查项 | 负责人 | 状态 |
|------|--------|--------|------|
| 1 | | | ⬜ |
```

### Step 4: 填充内容

根据主题特点：
1. 填充第 2 章背景（结合搜索结果/内部资料）
2. 填充第 3 章核心概念（术语定义 + 原理解释）
3. 填充第 4 章方案对比（至少 2-3 个主流方案，维度不少于 5 个）
4. 填充第 5 章实施建议（必须给出明确推荐，不可模棱两可）
5. 填充第 6 章风险评估（至少 3 项风险）

### Step 5: 执行纪律检查

1. `check-doc-structure` → 验证文档结构完整性
2. `check-markdown-format` → 验证格式
3. `check-chinese-typography` → 验证中文排版
4. `check-doc-placement` → 验证在新技术调研目录下
5. `check-content-quality` → 验证无占位符
6. `generate-checklist` → 根据内容生成检查清单补充第 7 章

### Step 6: 输出结果

```
✅ 技术调研文档创建完成
📄 路径：docs/03-技术笔记/新技术调研/<主题>-调研.md
📊 纪律检查：全通过
💡 提示：请审阅第 4 章方案对比数据的准确性
```

## 失败处理

| 失败场景 | 处理方式 |
|---------|---------|
| 主题过于宽泛（如「前端」） | 询问：请指定具体方向，如「前端构建工具选型」 |
| 缺少对比方案数据 | 执行 WebSearch 补充，仍不足则标记为「待补充」并提示用户 |
| 无法给出推荐结论 | 列出各方案适用场景，由用户决策 |
