## 功能说明

本 Skill 不负责「检查」，而是作为 **辅助工具**，在以下场景生成可执行的检查清单：
1. User-invoked Skill（如 `/create-research-doc`）创建文档完成后 → 生成末尾检查清单
2. User-invoked Skill（如 `/submit-docs`）提交完成后 → 生成 MR 评审检查清单
3. User-invoked Skill（如 `/audit-all-docs`）审计完成后 → 生成改进优先级清单
4. 单独调用：为某篇已有文档补全缺失的「落地检查清单」章节

## 场景 1: 为不同文档类型生成章节检查清单

根据文档所在目录，生成对应维度的检查项（默认插入到文末 `--- 文档结束` 之前）：

### 模板 A: 00-开发规范类文档（规范类文档）

```markdown
## N. 落地检查清单

| 序号 | 检查项 | 级别 | 检查方式 | 责任人 |
|------|--------|------|---------|--------|
| 1 | 所有【强制】规则是否均有明确的可执行示例 | 强制 | 人工评审 | 文档作者 |
| 2 | 所有【禁止】规则是否均有反面示例 | 强制 | 人工评审 | 文档作者 |
| 3 | 是否包含完整的代码示例（正反例对比） | 推荐 | 人工评审 | 文档作者 |
| 4 | 规范中涉及的命令/配置是否本地测试通过 | 强制 | 本地验证 | 文档作者 |
| 5 | 落地检查清单是否 ≥ 10 项 | 强制 | Skill自动检查 | 文档作者 |
| 6 | 检查项是否覆盖了文档中的所有【强制】规则 | 强制 | 人工评审 | 评审人 |
| 7 | 检查方式是否具体可操作（非「检查」二字空话） | 推荐 | 人工评审 | 评审人 |
| 8 | 各团队是否明确了责任人角色 | 强制 | 人工评审 | 架构组 |
| 9 | 是否与现有规范无冲突（跨文档一致性） | 强制 | 交叉评审 | 架构组 |
| 10 | 规范是否通过了至少 1 位非作者的评审验证 | 强制 | MR流程 | 评审人 |
```

## 场景 2: 基于 Git 提交变更生成 MR 评审清单

当调用方是 `/submit-docs` 时，生成 **MR 评审检查清单**（输出到终端，不写入文档）：

```markdown
## 📋 MR 文档评审检查清单

### 基础规范检查
- [ ] 文档头部信息表完整（版本、日期、适用范围、作者）
- [ ] 文档归入正确的 6 类编号目录
- [ ] 标题层级无跳级、结尾标记完整
- [ ] 中文排版合规（中英文空格、全角标点）
- [ ] 代码块均指定了语言类型
- [ ] 无占位符文本「（待补充）」「TODO」等

### 内容质量检查
- [ ] 文档内容符合该目录下的内容特征要求
- [ ] 方案类文档包含方案对比（≥2方案 × ≥5维度）
- [ ] 规范类文档包含落地检查清单（≥5项）
- [ ] 代码示例可执行、无明显错误
- [ ] 事实性数据有来源标注（如适用）

### 引用与资源检查
- [ ] 内部文档引用均使用相对路径（无 GitHub 绝对 URL）
- [ ] 交叉引用的文档真实存在（无死链）
- [ ] 图片资源存放于 assets/images/ 目录（无外部图床 URL）

### 提交规范检查
- [ ] 提交信息符合 `docs(模块): 描述` 格式
- [ ] 分支命名符合 `docs/xxx` 或 `trae/agent-xxx` 格式
- [ ] 单次提交只包含一个逻辑单元（建议变更 ≤ 500 行）
- [ ] 已在本地执行 `/audit-all-docs` 或相关检查
```

## 自动修复逻辑

### 文档缺少检查清单章节 → 自动追加

条件：
1. 文档是 `00-开发规范/`、`03-技术笔记/**`、`02-部署运维/` 下的文档
2. 文中未出现「落地检查清单」的二级/三级标题

动作：
1. 读取文档最后 10 行，定位到标准结尾标记之前
2. 根据文档所在目录选择模板 A / B / C / D
3. 插入（章节编号自动递增：如现有最后一章是「## 7. 风险评估」→ 插入「## 8. 落地检查清单」）
4. 标记 `autofixed: true`
